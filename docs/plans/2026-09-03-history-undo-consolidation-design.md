# 操作日志与撤回整合设计

## 目标

减少顶部导航和功能页面中的重复表达，将撤回能力作为操作日志的一部分：用户选择一条历史记录后，在同一详情工作区查看记录、检查撤回条件并执行整批撤回。

## 方案比较

### 方案 A：统一日志状态与详情工作区（采用）

把撤回检查、执行和刷新并入 `history` 状态仓库；日志详情组件同时呈现操作明细和撤回操作。删除独立撤回导航、路由、页面、状态仓库和专属面板。

优点是只有一个历史入口，选择状态、详情状态和撤回状态共享同一操作编号，不会出现两个页面各自加载同一列表的问题。后端撤回命令、日志协议和安全检查继续复用，因此不会降低安全边界。

### 方案 B：保留撤回仓库，把旧面板嵌入日志页

开发量较小，但两个状态仓库会同时维护当前操作编号，专属撤回资源仍然存在，不符合删除重复资源的目标。

### 方案 C：在操作日志中增加“详情 / 撤回”标签

能保留完整撤回表格，但用户仍需在同一记录内切换两个相似页面，信息结构依然重复，且窄屏布局复杂度更高。

## 信息架构

- 顶部导航仅保留“文件名管理”“操作日志”和“帮助”。左侧不再显示独立产品标题。
- 文件名管理左栏直接从第一步“选择目录”开始，不保留弱提示性的“文件名管理流程”标题。
- 操作日志保持左侧记录列表、右侧详情布局。
- 右侧详情包含操作状态、规则、时间、逐项结果，以及底部的撤回状态和动作。
- 可撤回记录显示安全检查摘要和“确认整批撤回”；已撤回、不可用或存在风险时显示对应状态，不提供错误动作。

## 状态与数据流

选择日志时，日志仓库以同一操作编号并行读取日志详情和撤回预检。撤回按钮只在预检状态为“可撤回”时启用。执行完成后重新读取详情、撤回状态和当前筛选条件下的日志列表，确保列表标签、详情内容和撤回提示一致。

独立 `/undo` 路由及其 Vue 页面、Pinia 仓库、组件和测试删除；Rust 撤回服务、Tauri 命令和桌面 API 保留，作为操作日志内撤回能力的底层实现。

## 错误与忙碌状态

日志列表加载、记录详情读取、撤回预检和撤回执行分别恢复各自忙碌状态。预检失败时详情仍可查看，并在撤回区显示可读错误；撤回失败不清空当前记录，允许用户核对后重试。

## 验证

- 组件测试确认顶部不再出现重复产品标题和撤回管理入口。
- 页面测试确认左侧流程标题移除。
- 状态测试覆盖选择日志同步预检、仅允许安全记录撤回，以及撤回后刷新列表和详情。
- 端到端测试确认操作日志是唯一历史入口，页面内存在撤回功能，旧导航和旧路由资源消失。
